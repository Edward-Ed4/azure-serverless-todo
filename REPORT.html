1. Introduction

Cloud computing has transformed how software applications are built, deployed, and scaled. Instead of managing physical servers, developers can now leverage cloud platforms to host applications that are globally available, highly scalable, and cost-effective. This project demonstrates the practical application of cloud computing concepts by building and deploying a fully functional serverless web application called CloudTasks using Amazon Web Services (AWS).

CloudTasks is a To-Do List web application that allows users to create, view, and delete tasks through a browser-based interface. The application is built entirely on cloud services with no traditional servers required.

2. Project Objectives

  • Design and deploy a cloud-native web application using AWS services
  • Demonstrate the use of serverless computing through AWS Lambda
  • Implement a REST API using Amazon API Gateway
  • Host a static frontend on AWS S3 with global delivery via Amazon CloudFront
  • Integrate a cloud-hosted NoSQL database (MongoDB Atlas) for persistent data storage
  • Apply cloud computing concepts including scalability, elasticity, and pay-as-you-go pricing

3. Cloud Architecture

The application follows a three-tier serverless architecture:

[User Browser]
      |  HTTPS
      v
[Amazon CloudFront - CDN]
      |
      v
[AWS S3 - Static Website Hosting]
      |  REST API calls
      v
[Amazon API Gateway]
      |  Lambda Proxy Integration
      v
[AWS Lambda Functions (Node.js 22.x)]
      |  MongoDB Driver
      v
[MongoDB Atlas - Cloud NoSQL Database]

3.1 Architecture Summary

Layer Service Role

4. Services Used

4.1 Amazon S3 (Simple Storage Service)

Amazon S3 is an object storage service that offers scalability, data availability, and security. In this project, S3 is used to host the static frontend files (HTML, CSS, JavaScript) with static website hosting enabled. The bucket cloudtasks-frontend-2026 is configured with public read access.

Key features used:

  • Static website hosting
  • Public bucket policy for read access
  • Object storage for web assets (HTML, CSS, JavaScript)

4.2 Amazon CloudFront

Amazon CloudFront is a fast content delivery network (CDN) service that securely delivers data with low latency and high transfer speeds. CloudFront was added to provide HTTPS access and global availability. Without CloudFront, the S3 website URL only supports HTTP and may be inaccessible in some regions.

Distribution domain: https://d18dq5screwix.cloudfront.net

  • HTTPS delivery with TLS encryption
  • Global edge locations for fast access worldwide
  • Origin: S3 static website endpoint

4.3 AWS Lambda

AWS Lambda is a serverless compute service that runs code without provisioning or managing servers. Lambda automatically scales based on the number of requests. Three Lambda functions were created:

Function Name HTTP Method Purpose
cloudtasks-get-todos GET Retrieves all tasks from the database ordered by date
cloudtasks-create-todo POST Creates a new task and saves it to the database
cloudtasks-delete-todo DELETE Deletes a specific task from the database by ID

Each function is written in Node.js 22.x and uses the MongoDB driver to connect to Atlas. Environment variables store the database credentials securely.

Key features used:

  • Serverless execution — no server management required
  • Node.js 22.x runtime
  • Environment variables for secure configuration
  • Pay-per-invocation pricing — costs nothing when idle
  • Automatic scaling to handle any number of requests

4.4 Amazon API Gateway

Amazon API Gateway is a fully managed service for creating, publishing, and maintaining REST APIs. It acts as the entry point for all HTTP requests, routing them to the appropriate Lambda function.

Method Endpoint Lambda Function
GET /Prod/todos cloudtasks-get-todos
POST /Prod/todos cloudtasks-create-todo
DELETE /Prod/todos?id={id} cloudtasks-delete-todo

API Base URL: https://zvzesiqv22.execute-api.eu-north-1.amazonaws.com/Prod

Key features used:

  • REST API with Lambda proxy integration
  • CORS configuration for browser access
  • Regional endpoint in eu-north-1 (Stockholm)
  • Prod deployment stage

4.5 MongoDB Atlas

MongoDB Atlas is a fully managed cloud database service. A free tier M0 cluster was created in Frankfurt (eu-central-1). MongoDB Atlas stores each task as a document in a NoSQL collection.

Database configuration:

  • Cluster name: cloudtasks-cluster
  • Database: TodoDB
  • Collection: todos
  • Network access: open to all IPs (0.0.0.0/0) for Lambda connectivity

Document structure:

{
  "id": "uuid-string",
  "title": "Task title text",
  "completed": false,
  "createdAt": "2026-06-05T08:00:00.000Z"
}

5. Application Features

  • View Tasks: On page load, all existing tasks are fetched from the cloud database and displayed
  • Add Task: Users type a task title and click "Add Task" to save it to MongoDB Atlas
  • Delete Task: Each task has a delete button (✕) to remove it from the database
  • Real-time feedback: Loading spinners, error messages, and empty state indicators
  • Responsive design: Works correctly on both desktop and mobile browsers
  • Student identification: Footer displays student name, registration number, and student number

6. Implementation

6.1 Frontend

The frontend is a single-page application built with plain HTML5, CSS3, and vanilla JavaScript. No frontend framework was used, keeping the application lightweight and fast. The JavaScript uses the browser's Fetch API to communicate with the API Gateway endpoints.

6.2 Backend (Lambda Functions)

Each Lambda function follows this pattern:

  1. Parse the incoming HTTP request from API Gateway
  2. Connect to MongoDB Atlas using a cached client connection
  3. Perform the required database operation (query, insert, or delete)
  4. Return a properly formatted HTTP response with CORS headers

Connection caching reuses the MongoDB client across warm Lambda invocations to reduce connection overhead and improve response times.

6.3 Security

  • MongoDB credentials are stored as Lambda environment variables, not in source code
  • CORS headers are configured on both Lambda and API Gateway
  • S3 bucket policy allows only public read access to objects
  • CloudFront enforces HTTPS for all connections
  • MongoDB Atlas IP access list controls which sources can connect

7. Deployment Process

  1. Created an AWS account with the Free tier (6 months, $200 credit)
  2. Created an S3 bucket (cloudtasks-frontend-2026) with static website hosting enabled
  3. Created three AWS Lambda functions with Node.js 22.x runtime
  4. Uploaded function code as ZIP files containing the handler and MongoDB driver
  5. Configured environment variables (MONGODB_URI, MONGODB_DATABASE) on each Lambda function
  6. Created an Amazon API Gateway REST API (cloudtasks-api) with a /todos resource
  7. Added GET, POST, and DELETE methods with Lambda proxy integration enabled
  8. Enabled CORS on the API Gateway for browser access
  9. Deployed the API to a "Prod" stage
  10. Created a MongoDB Atlas free M0 cluster and configured network access
  11. Created database TodoDB and collection todos
  12. Uploaded frontend files to S3 and applied public read bucket policy
  13. Created a CloudFront distribution for global HTTPS delivery
  14. Pushed all source code to GitHub repository

9. Challenges Encountered

9.1 Azure Region Restrictions

The project initially targeted Microsoft Azure using an Azure for Students subscription. However, the subscription had severe region restrictions that prevented deployment of Azure Static Web Apps, Azure Functions, and Azure Cosmos DB in any of the available regions. After exhausting all available region options, the project was migrated to AWS, which provided better region availability and fewer restrictions.

9.2 Lambda Handler Configuration

Initially the Lambda handler was set to the default index.handler instead of the function-specific handlers (getTodos.handler, createTodo.handler, deleteTodo.handler). This caused a Runtime.ImportModuleError that was identified through CloudWatch logs and resolved by updating the runtime settings for each function.

9.3 API Gateway CORS Configuration

Cross-Origin Resource Sharing (CORS) needed to be explicitly configured on the API Gateway to allow browser requests from the S3-hosted frontend. Without proper CORS headers, browsers blocked all API responses.

9.4 Lambda Proxy Integration

The API Gateway required Lambda proxy integration to be enabled for each HTTP method to correctly pass requests to Lambda and return responses to the client. Without this setting, API Gateway returned raw Lambda output instead of proper HTTP responses.

9.5 CloudFront Origin Configuration

The CloudFront distribution initially pointed to the S3 bucket endpoint instead of the S3 website endpoint. This was corrected by updating the origin to use the website endpoint, enabling proper routing of requests to index.html.

11. Conclusion

This project successfully demonstrates the design and deployment of a cloud-native serverless web application using Amazon Web Services. The CloudTasks application leverages five AWS and cloud services: AWS Lambda for serverless compute, Amazon API Gateway for REST API management, AWS S3 for static website hosting, Amazon CloudFront for global HTTPS content delivery, and MongoDB Atlas for cloud database storage.

The project illustrates key cloud computing concepts including serverless architecture, managed services, auto-scaling, elasticity, and the pay-as-you-go pricing model. The application is fully functional, publicly accessible from anywhere in the world, and requires zero server management — demonstrating the power and simplicity of modern cloud platforms.

Despite challenges encountered during deployment — particularly with Azure region restrictions — the project was successfully completed by adapting to use AWS services, demonstrating the importance of flexibility and problem-solving in cloud engineering.
